## 1. 預設席位與供應商 id 之漂移:啟動期會爆、與仍會靜默失效的形狀

本套件的 AI 席位(`relate.ai`、`relate.reverse.ai`、重評與判定小組各席;`use`／`fallback` 皆為供應商條目 id)由 AI 調度層(抓取套件之 `createAiAdapter`,底層為 `w-dispatch-ai` 的**內建目錄** `src/providers.mjs`)解析;`cfg.aiOptions.providerPick` 是使用端給的「可用池」(`ai` 段**不收** `providerPick`,給了即拋:`test/unit-settings.test.mjs`「ai 段不收 providerPick」案)。id 寫錯的後果依形狀分,原經驗記為「第二種靜默、更難察覺」,現行抓取套件已將它改為拋錯(其 `chainFor` 註解:靜默略過會讓鏈莫名變短):

| 形狀 | 後果 | 察覺方式 |
|---|---|---|
| `aiOptions.providerPick` 列了內建目錄(與 `ai.extraProviders`)**沒有**的 id | 建構調度層即拋「ai.providerPick 含未知 id：…」(附最接近之拼寫)→ `createKnowledgeRelate` 建構失敗、整輪不執行 | 建構期例外 |
| 席位(`use`／`fallback`)引用了不可用的條目(目錄無此 id、未列於 `providerPick`、缺金鑰) | 啟動期席位檢核拋「AI 席位於啟動期檢核失敗（N 席）：<席位路徑> → 席位引用了不可用的條目：…」 | 建構期例外;`test/unit-relate-assembly.test.mjs` 以 `no-such-model-free` 兩案釘住 |

注入 `cfg.aiAdapter` 時席位檢核屬注入方(其具 `validateSeats` 才檢,README §8):替身或自組調度層若不驗,舊的靜默形狀會重現。

**真正仍會靜默失效的有兩種**:①條目還在目錄、但上游改政策使它 100% 失敗(§1.1);②字面(預設值、夾具、文件範例、評比表)與目錄脫節——不影響執行,只在升版後某天才紅或誤導。

**「上游把條目下架或改名,而設定／預設／夾具還留著舊 id」是反覆發生的同一形狀**(免費條目被移除、改名、限時窗口結束後下架、整族條目移除、免費變體終止,已發生五次以上)。其中最難纏的是**套件內建預設也含舊 id**:曾經不是生產事故抓到的,而是單元測試突然紅了才發現。另有一條限時免費條目**加入隔日即下架**(加入時已在註解預告這個形狀,當日即應驗)。

**本套件的落地與守門**:

- 預設席位 `relate.ai = { use: 'oc:opencode/mimo-v2.6-flash-free', fallback: ['oc:opencode/big-pickle'] }`(`src/core/relateSettings.mjs`)只能用 `w-dispatch-ai` **內建目錄**之 id:零設定安裝沒有 `extraProviders`,寫進去就是建構即拋。守門:`unit-settings`「免費 AI 為主」案(逐 id 查 `w-dispatch-ai/src/providers.mjs`,須為匿名免金鑰之 opencode 條目)與 `unit-relate-assembly`「套件預設席位須可解析」(`createKnowledgeRelate({ workDir })` 不拋)。目錄一移除即紅。
- **升版後要對齊的字面有四處**:①預設席位(`src/core/relateSettings.mjs`)與 README §5／§8 之範例;②評分受測名單(`RELATE_BENCH_MODELS` ＝預設席位＋抓取套件之 `DEFAULT_FREE_MODELS`,`src/bench/relateBench.mjs`;`unit-relate-bench`「受測名單」案釘住同一推導);③測試中引用目錄 id 之字面(`unit-settings`、`unit-relate-assembly`、`unit-relate-log-contract`);④**opencode 額度日誌之夾具 modelID**:`ai.pools.oc` 之日誌夾具 `modelID=mimo-v2.6-flash-free`(`unit-relate-assembly`、`unit-relate-log-contract`)對不到目錄條目時,調度層不發「供應商額度：」字樣——**升版後全套才紅**,只看設定的檢查看不到。
  - 盤點:`git grep -nE "mimo-v2|big-pickle|modelID=" -- src test README.md toolg` → 現況 11 行(README 2、`src/bench/relateBench.mjs` 2〔JSDoc 範例〕、`src/core/relateSettings.mjs` 1、`unit-relate-assembly` 2、`unit-relate-log-contract` 2、`unit-settings` 2);升版後逐行對目錄。
- **評比表是歷史記錄,不保證 id 仍在目錄**:套件根之 `模型評比.csv` 留有已自目錄移除之條目之列(muse、space-bunny、ling、longcat 等,`w-dispatch-ai` 1.0.65 之目錄已無),不影響執行,但重跑評分時以目錄為準。
- 上游移除條目後,仍引用它的舊設定曾長期靜默落到遞補而無人察覺(舊調度層每次呼叫即敗再遞補);現行調度層建構即拋,但**條目還在而一直失敗**者(§1.1)仍只留痕跡於日誌:`ai.healthStreak` 之健康降序事件(「供應商健康：」WARN)。

### 1.1 第三種形狀:條目還在,但上游改政策使它 100% 失敗

2026-09 中旬起,**opencode 自家免費層**對外斷供(上游維護者明示為反濫用政策;`w-dispatch-ai/src/providers.mjs` 檔頭〈Zen 免費層閘門〉有判定依據與診斷流程):CLI 回 exit 1、REST 回 HTTP 403,訊息一致——

> `Error from provider (Console): OpenCode's free tier can only be used from within OpenCode`

**斷供範圍的分界線是「金鑰屬於誰」,不是「走不走 opencode CLI」**——這點一開始判斷錯,經逐條目實測才釐清。條目 id 的第二段即供應商:

| 實測(逐條目 id 單打並印 stderr;條目名依當時目錄,muse、deepseek-v4-flash-free、`zen:` 條目今已自目錄移除) | 金鑰／供應商 | 結果 |
|---|---|---|
| `oc:opencode/muse-spark-1.3-contributor-free`(CLI) | `OPENCODE_KEYS`／`opencode` | ✗ 11s exit 1 |
| `zen:muse-spark-1.3-contributor-free`(REST) | `OPENCODE_KEYS` | ✗ 1s HTTP 403 `FreeTierError` |
| `zen:mimo-v2.5-free`(REST) | `OPENCODE_KEYS` | ✗ 403 同訊息 |
| `oc:opencode/deepseek-v4-flash-free`(ds4f) | `OPENCODE_KEYS`／`opencode` | ✗ 5s exit 1 `UnknownError` |
| **`oc:agnes-ai/agnes-3.0-flash`(CLI)** | `AGNES_KEYS`／`agnes-ai` | **✓ ok 14s** |
| **`oc:poolside/poolside/laguna-s-2.1`(CLI)** | `POOLSIDE_KEYS`／`poolside` | **✓ ok 8s** |

即:**被擋的只有 `provider: 'opencode'`(`OPENCODE_KEYS`)那一族**;用自己的 agnes／poolside 金鑰走 opencode CLI 完全正常——opencode 此時只是傳輸層,請求送到各自家的端點。**沿用本機 `auth.json` 登入亦被拒**(對 opencode 那族而言不是金鑰問題,是政策)。

**因此 `oc:agnes-ai/*` 與 `oc:poolside/*` 是同一上游帳號的替代傳輸路徑**:直連 REST 端點劣化時可改走它,但**不增加額度也不增加多樣性**(同一帳號、同一模型),排席位時不可當成另一家。

**其後解除**:閘門是以**「呼叫端的 config 裡有沒有 bash 工具」**判定是不是 opencode 本體;`w-dispatch-ai` 改為注入 `OPENCODE_CONFIG_CONTENT` 且 `bash: 'ask'`(而非 `'deny'`;`providers.mjs` 之 `OC_READONLY = { edit: 'deny', bash: 'ask' }`)即通過。但這條路的性質要記清楚:

- **只有 CLI(`oc:`)路徑通,REST(`zen:`)仍 403**——REST 無法偽裝成本體。
- **它依賴上游目前的偵測方式**:上游只要改判定(例如改檢查別的特徵),就會再次斷供。故**不把某一家放到太多席**,且遞補鏈要保留非 opencode 家。**本套件的預設席位 use 與 fallback 同為 opencode 免費層(單一故障域)**,使用端宜在 `fallback` 尾端加入非 opencode 家(README §8)。
- `oc:opencode/deepseek-v4-flash-free`(ds4f)**不在此列**:它回的是 `UnknownError` 伺服器錯誤,與閘門無關,閘門解除後仍不可用。

**這種形狀比「條目被移除」更難察覺**:id 解析正常、啟動期無警告、只比對目錄的升版檢查也不會報——能看出的是調度層之健康降序事件(連續 ≥`ai.healthStreak` 次整組皆敗即降至鏈尾並以「供應商健康：」WARN 寫入當輪日誌)與各段「無進度」。曾有一家身兼三個席位,每輪白繳 18 次失敗再全數遞補到有 session 上限的付費家,連續 10 輪無人發現。

**教訓與作法**:

- 〔教訓 1〕**每次升版 `w-dispatch-ai`(或抓取、摘要套件)後,先跑 `unit-settings`、`unit-relate-assembly` 兩檔**——前者驗預設席位仍在目錄、後者驗預設可解析與額度日誌夾具;不要只看 `npm i` 成功。**但它們只抓「條目被移除」,抓不到 §1.1 那種政策變動**(條目仍在目錄、解析正常,只是 100% 失敗)——該形狀只有真呼叫(`node src/bench/cli.mjs --role relate --models <id> --runs 1`,會呼叫真 AI)或健康降序事件看得出來。
- 〔教訓 3〕**限時免費條目視同易失物**:採用前先想好下架時的退路(誰承接、遞補鏈夠不夠長),並預期它隨時消失,壽命可以短到一天。**倒掉的是 opencode 自家免費層,不是「免費模型都沒了」**——這句話第一次寫錯過,更正即上文。本套件預設遞補 `big-pickle` 為目錄收錄之免費條目(`w-dispatch-ai` 之 `providers.mjs` 檔頭載其收錄經過:官方確為免費,但壽命無保證),同樣視同易失物。
- 〔教訓 4〕**同一家不要同時坐太多席**:一家倒下就空了多個席位,全部壓到遞補。排席位時看的不只是分數,還有**故障域**——一家死掉會空幾席、遞補後是否仍滿足換家原則。
- 〔教訓 5〕「不重要」的備查／示例用條目(如已知不可用但留著登錄、文件與測試中的範例 id)同樣會因目錄變動而失效,**留著就要跟著上游變動維護**,否則不如刪掉。
- 〔教訓 6〕`extraProviders`(使用端自帶條目)與內建目錄**不要同時定義同一個模型**——兩處定義必然漂移;套件收錄之後就移除自帶的那份。接自帶條目要**每個建立調度層之處都帶到**(兩處不一致即「missing」誤報)。**套件預設(`RELATE_DEFAULT`)只能用內建目錄之 id**——零設定安裝沒有 `extraProviders`,寫進去就是啟動即拋。另:訂閱制 CLI 帳號與使用者本人共用額度,額度緊時不要跑它的評比。
- 〔教訓 7〕**小探測成功 ≠ 實際題可用;REST 條目「HTTP 200 卻 missing content」先懷疑傳輸,不要先懷疑模型**:開工前探測(小 JSON)2.1s 正確,正式評比 14 題卻全敗。直打重現:HTTP 200、本體是 brotli 壓縮位元組、回應**沒有 `Content-Encoding` 標頭**(Node fetch 看到 0 個標頭)——fetch 不解壓 → 轉接器 JSON 解析失敗 → `INVALID_RESPONSE: missing choices[0].message.content`;以 brotli 手解即為完整正確之答案(finish_reason=stop),改帶 `Accept-Encoding: identity` 則直接回原文 JSON。小回應未被壓縮,所以探測過得了。**診斷法**:把原始回應以位元組讀出,印全部標頭與前 16 bytes hex,逐一試 gunzip／inflate／brotli／zstd。我先猜「推理 token 吃光 max_tokens」,是錯的——沒看原始回應就猜成因,正是這條要擋的。
   **同形第二例是生產故障**:另一家 REST 條目長回應被 gzip 壓縮而無標頭(前 bytes `1f8b`),只有短回應的呼叫不受影響。`w-dispatch-ai` 之三個 REST 轉接器現已預設帶 `Accept-Encoding: identity`(2026-09-24 起;`dispatchApiOpenaiCompat.mjs` 檔頭〈預設帶Accept-Encoding: identity〉)根治。**同一條目「短回應正常、長回應全敗」即此症之指紋**。
- 〔教訓 8〕**讀遞補結果之錯誤訊息要看「最後一筆」是哪一把金鑰的**:同一條目有多把金鑰時,`INVALID_RESPONSE`／HTTP 錯誤會換下一把、以**剩餘預算**重打(`TIMEOUT`／驗證失敗才整組跳過,`w-dispatch-ai/src/dispatchAiFallback.mjs` 檔頭〈失敗分流〉)。故評比格記「TIMEOUT after 66.9s」而該格實耗 360s,表示第一把先以別的錯誤失敗、第二把用剩下的 67s 逾時——第一次就逾時的會是「after 360s」。只看最後一筆會把傳輸缺陷誤讀成「模型太慢」。


## 2. prompt 長度上限:安靜失敗、0ms、不計入逾時

`agy:`(antigravity CLI)**以命令列傳 prompt**,`w-dispatch-ai/src/dispatchAntigravity.mjs` 設 `MAX_PROMPT_LENGTH = 30000`(Windows 命令列 32,767 上限扣掉 exe 路徑與旗標之保守值)。超過就**未執行即回失敗**(errorType `params`),耗時接近 0ms——不像逾時那樣顯眼,實際效果是「那個席位從來沒真的工作過」。`params` 不計入健康降序之連續失敗(進入執行前即被擋,不會因冷卻而改善),僅另計 mismatch 供執行摘要揭露(抓取套件 `src/core/ai/providerHealth.mjs`)。

**本套件最容易踩**:一批 `relate.notesPerCall`(6)篇、每篇 `relate.candidatesPerNote`(預設 25)個候選:

| 呼叫 | 實測 prompt 長度 | 結果 |
|---|---|---|
| 正向關聯(6 篇 × 25 候選) | **40,191～43,814 字元** | 超過 30,000:命令列型席位每次都 params,全由遞補承接。候選數改 15 後為 25,017～27,732,主力可用 |

**處置路徑**:

- 本套件之六類呼叫皆走 `ai.callJson`(`src/stages/relateAiCall.mjs`)→ 經抓取套件 `src/core/ai/capability.mjs` 之 `fitChain`,**呼叫前**依實際 prompt 長度(含防寫前綴)把放不下之條目剔除,直接改派遞補,不產生失敗紀錄,只以「供應商能力：」WARN 與 oversize 計數揭露;**全鏈條目皆放不下**時不送出,回 `oversize: true` 之失敗(「超過本席位全部條目之上限」)。此預篩由建構選項 `capability: true` 開啟(`src/createKnowledgeRelate.mjs` 之 `AI_ADAPTER_OPT`);**注入 `cfg.aiAdapter` 時不接**(調度層屬注入方)。啟動期另對「全鏈條目皆有長度上限」之席位警告(`unit-relate-assembly` 該案釘住)。

**教訓**:註解裡寫的「約 1.5 萬字」實測低估三倍(本套件 `src/core/relateSettings.mjs` 之註解載的是實測的 4.0～4.4 萬)。**prompt 長度一律實測**,不要憑印象估;改動 `candidatesPerNote`、`notesPerCall`、席位數或提示詞模板時都要回頭重量(量法:以實際筆記經 `domain.buildPrompt(targets, candidateMap)` 組出提示詞後量 `.length`,組法見 `test/tools/promptFixtures.mjs`)。


## 16. 測試之 cwd 與「匯入即執行」

- **形狀**:會 `import()` 或執行所掃到之檔案的測試,若以 cwd 為掃描根(`path.resolve('.')`),從別的目錄(例如使用端專案根)直跑套件測試檔時,掃描根就變成別處,匯入到別處的入口腳本;腳本頂層若有副作用(頂層 await 跑管線、寫庫),**「import 它」等於「執行它」**。曾有此事故:自使用端專案根直跑一支套件的入口匯出測試,逐檔 import 掃到使用端的觸發腳本,在排程停用期間啟動了一輪正式管線(執行鎖照取、日誌照寫、呼叫了一次免費 AI,事後以行程命令列與用量計數界定影響並回退)。以 BFS 順序,入口腳本先於暫存工具被匯入並以頂層 await 卡住其後之匯入——否則暫存目錄內的寫庫腳本也會被執行。
- **成因(流程)**:①套件測試不在套件根執行——為省一次 `env -C` 改從使用端專案根跑;②測試以 cwd 為掃描根。
- **修正**:所有會列舉原始碼並 `import()` 之測試,根一律取自模組位置:`path.resolve(path.dirname(fileURLToPath(import.meta.url)), '..')`(規則帳本 GEN-09;本套件 `unit-relate-entry`〔檔頭明載「本測試會 import(＝執行)根下每一支 .mjs,套件根須與 cwd 無關」〕、`unit-relate-package`、`unit-relate-bench`、`unit-relate-registry`、`unit-relate-holds` 皆如此)。**通則:會 import 或執行所掃到之檔案者,根一律取自模組位置;入口腳本之頂層副作用使「import 它」等於「執行它」**,故命令列／入口腳本須以直接執行判定守門:本套件 `src/bench/cli.mjs` 以 `isDirectRun(import.meta.url)` 守門,被 import 時不執行,`unit-relate-bench` 另起行程只 import,驗「無輸出、離開碼 0」。
- 套件測試一律自套件根跑(`npm test`,README §15)。依 cwd 找測試的執行器,工作目錄一錯就跑成另一個對象——要指定根時用 `npm --prefix <根> test`,不靠當下 cwd。
- 盤點:`git grep -nE "path\.resolve\('\.'\)|readdirSync\(\s*'\.'|process\.cwd\(\)" -- test src toolg` → 應為空(現況 0 命中)。

## 18. 關聯:邊庫為真理、兩端投影、變更與刪除

- **「以該篇為準重判、未重選即刪」會大量刪有效邊**:選擇式 prompt(每篇最多選 `maxRelationsPerNote`〔4〕條、候選 `candidatesPerNote`〔預設 25〕)不是逐邊裁決——度數 >4 之筆記一經重判必失去(度數−4)條,度數大於候選數者連沒展示給 AI 的鄰居都會被當「未重選」刪掉,且他篇提出之入邊一併被刪。**「沒選」不等於「判定無關」;撤銷只能來自逐邊之明確裁決**。故內容變更之重判**只增不刪**(REL-10:可新增、可升為衝突,不改既有邊之型、不撤銷),既有邊之改型／撤銷走逐邊重評(兩席逐邊 keep／change／retire、兩評一致＋不同供應者＋分級閘門 `relate.reeval.apply`;REL-13)。
- **偵測端與判定端讀的必須是同一份資料**:關聯 prompt 讀記錄之標題、類別、概念、`summary` 等(`src/domain/relateDomain.mjs` 之 `targetLines`／`candidateLine`;記錄只存 300 字之一句話重點,全文在 md);只偵測 md 而不同步回記錄,重判看到的仍是舊內容。反過來,正文其他章關聯根本不讀,改了也不該觸發——**變更偵測之範圍＝判定之實際輸入**(建置系統之動作鍵原則)。偵測在摘要套件之內容同步子階段(`sync`,寫記錄之 `knowledgeChangedAt`),本套件只比對版本(下一條)。
- **「是否已評估」用版本相等,不用時間先後**:各輪若在同一秒內完成,`knowledgeChangedAt > relatedAt` 因字串相等而漏判(生產輪距長不易遇到,但時鐘回撥、同秒偵測與評估一樣會錯)。改為評估時記下 `relatedChangeAt`(＝當時之 `knowledgeChangedAt`),兩者不同即待重判(`src/stores/relatedNotes.mjs` 之 `needsReeval`／`needsEdgeReview`;REL-10)——**時間戳只拿來顯示,判斷狀態一律比版本**。
- **合併代數要窮舉證明,左折疊不夠**:三提案之全排列都相同,仍可能在「a ⊕ (b ⊕ c)」時遺失 b⊕c 之 history(incoming 之 history 被忽略),且理由不同之同序提案無決勝(先到者勝)。以 40 提案池 9,880 組三提案 × 6 排列 × 兩種括號窮舉才抓到(`test/unit-relate-edges.test.mjs`「mergeEdge 窮舉」案;全序以理由為最終決勝)。**可交換／可結合只對完整全序模式成立**(`allowTypeChange: true`);跨輪「只升不改」本就偏袒庫內,不宣稱代數性質(REL-04)。
- **非原子 replace 改單次原子寫入之 patch 的前提要寫成不變式並測**:`w-orm-lmdb` 之 patch 於單次原子寫入內 lodash merge——陣列依索引合併,只要 history 長度不減、每筆鍵集固定且值非 undefined、頂層不刪鍵,merge 結果即等於新值;另寫後回讀比對,不符退回 replace 再驗,仍不符拋錯(`src/stores/edgeStore.mjs` 之 `writeEdge`／`persistEdge`;REL-05)。前提由單元測試(任意合併序列 history 不縮短、鍵集固定;`writeEdge` 退回 replace 與拋錯案)釘住,而不是「看起來會對」。
- **舊工具會把新世代寫回舊格式**:邊 id 換身分(有序對 `sha1(from|to)` → 無序對 `sha1(min|max)`)後,仍用舊身分寫邊之舊修補工具一跑即重複。套件以「開工世代檢核 fail-closed」擋未遷移之庫(`generationMismatchOf`／`assertGeneration`:邊 id 非無序對雜湊者 >0 即 ERROR「關聯邊庫世代不符」、本段與投影不寫;REL-11),使用端自寫之一次性工具則須自加拒跑守門。**換身分／格式時,把所有寫入者列全(含一次性工具)**。
- **遷移要演練到「還原」**:本套件只檢核世代、不轉換(規則帳本 GEN-04);使用端若自寫遷移(如邊庫換身分),演練到可還原:複本上試跑 → 套用 → 重跑零變更 → 由備份還原並逐項比對遷移前之邏輯內容(邊、筆記記錄、md 雜湊)→ 從還原狀態再套一次,兩次結果逐項相同才上正式。**複本之筆記記錄存 md 之絕對路徑(`file`),不改指複本就會寫到正式 md**(投影與重評皆取記錄之 `file` 讀寫:`src/stores/noteProjection.mjs`、`src/stages/reevalSegment.mjs`)。
- **集合欄位之 patch 是深合併:陣列變短會殘留舊元素**:曾見摘要同步以 patch 寫概念,`[甲,乙]→[丙]` 落成 `[丙,乙]`、清空無效,卻只驗雜湊即記成功;處置為先 `concepts: null` 再寫新值並回驗實際欄位(在摘要套件)。本套件之重評進度與否決集合改存「版本\tid…」字串(`packIds`／`unpackIds`,`src/stores/reevalPolicy.mjs`:整值覆寫)。**`memStore` 是淺合併(`Object.assign`),會遮蔽此缺陷——凡涉 patch 語意之測試要用真 LMDB**(`unit-relate-edges`、`unit-relate-reeval` 之 `reviseEdge` 案皆用 `w-orm-lmdb`)。
- **判定之輸入要取全文來源,不取截斷之副本**:記錄之 summary 建立時截 300 字,重評要看變更後之完整「一句話重點」→ 讀 md(`summaryTextOf(readMd(n.file))`,與摘要同步同一實作,經 `src/core/summarizePackage.mjs`;`src/stages/reevalSegment.mjs`);md 讀不到即本輪不評、不記 tries、不佔名額(計 `reevalMdMissing`;不知道內容就不裁決)。
- **雙評之「獨立」以實際成交之供應者判,替身也要照實回**:測試替身之 `callJson` 一律回 providerId 'stub' → 兩評恆為同一家 → 一致之裁決永遠只記 same-provider,套用路徑在測試中永遠走不到。替身改回 `spec.use`(`test/tools/relateTestKit.mjs` 檔頭:providerId 取席位之 use;判定小組之席位給不同之 use)才測得到「兩評一致且不同供應者 → 套用」。
- **跨模組之帳(本套件寫、下游讀)要用正式組裝在同一輪跑一次**:例如衝突撤銷／降級事件帳(`src/stores/conflictEvents.mjs`,由本套件寫、下游據以重審其產物)。曾有一次首跑「下游沒排重審」——不是產品缺陷,是替身立爭議時引了批次前兩篇而非衝突兩端,依設計走「無爭議涉及 → 只移出已見衝突」分支。**替身要照真實模型會做的事寫,否則測到的是另一條分支**;先印 detail 計數再判,不憑印象改產品。本套件單獨驗不到下游之反應,故兩側各驗一半:本套件一側為契約測試(`unit-relate-contract`,下游可讀之產物格式與上游之變更通知),下游一側自驗其讀者。
- **退路不留日誌,就不能宣稱「生產沒發生過」**:`writeEdge` 之 replace 退路(patch 回讀不符才走;檔頭稱為先刪後插之兩次寫入,中途被砍會遺失該邊)觸發時**無任何日誌或計數**(`src/stores/edgeStore.mjs`:現況仍如此,只有回驗仍不符才拋錯),帳本只能寫「依不變式理論上不觸發、實況不可知」。凡有「例外時才走」之退路,先決定它被觸發時要留什麼痕跡(計數或 WARN)。
- **(通則)宣告完成前,把審定表逐條對照 `file:line` 核銷**:曾以為做完,寫帳本時回讀審定表才發現四項已裁定「採」卻沒落地(含判定輸入須取全文、振盪觀察計數等);同一輪又查出摘要句違反自寫之「新段附於句尾」契約、同一 JSONL 讀法手寫兩處(現為 `readAuditRows` 單一實作,`src/stores/relateLedgers.mjs`)。**審定表本身就是驗收清單**,不是只在動工前讀一次。
- **反向段需求以最終規則逐輪回放,不用平均外推**:曾以「每篇平均 N 對 × 每輪 M 篇」外推每輪需求並宣稱 P90 約 20,審查指出外推無據;以最終規則(kth 只排除衝突鄰居、資格看 o 之評估時刻;`src/stores/reverseCandidates.mjs`、REL-08)按建立時刻逐輪回放 7 日,才得每輪目標之分布(均值、P50、P90、最大)與 AI 次數、每篇計算耗時。開啟時之配額依回放之分布取(以 P90 為參考,高於均值),不取外推之平均;`relate.reverse.perRun` 預設 0(停用)。


## 19. 檢定標準:判準要能在真實庫上逐條核對

- **比率判準會把違規藏起來**:正體原以「簡體比例 ≥2%」判,改為「簡體專用字＋同形字誤用之處數＝0」後,同一庫量到的違規篇數增為約 9.5 倍(多數篇只有 1～3 字:给出、数据、软件)。**「有問題」要以數量定義,不以比例**——使用者裁示「禁止用機率去過濾或篩選」即此;本套件 RS3 同(簡體專用字、同形字誤用、誤用詞皆為 0;`src/standards/edgeStandards.mjs`)。

- **品質測試之素材要讓每條標準都走得到**:某品質測試原取「最新 N 篇」為素材,首跑 0 條衝突邊——衝突去向之標準在真實 AI 下完全沒被驗。改為「衝突對優先、其餘取最新」並凍結成固定題組(主組＋保留題組),兩批各有 3～4 條衝突邊,立爭議與非對立兩條路皆走到。**每條放行判準都要問:這份素材會不會讓它恆真?**(本套件題組各角色皆含保留題 5 案,README §14。)
- **判定小組之替身須讓各席之「實際供應者」不同**:共用替身以角色名當供應者,兩個覆核席會被判同一供應者 → 永遠未成立。替身之判定小組角色改以席位條目(`spec.use`)為供應者(`test/tools/relateTestKit.mjs`;`unit-relate-reeval` 之 `providers`)。
- **只驗一個專步之真實驗收,開跑前先唯讀試算選題**:為只跑某一專步,曾拉高選題門檻(最少篇數／待處理數／最長等待天數)來隔離,卻漏了另一條入選條件(既有待處理數 ≥ 每批篇數即入選),一開跑就是多組真 AI 批次。發現後立刻中止,並以行程清單確認無殘留 CLI 子行程。**改設定隔離前,先以同一組設定唯讀呼叫選池函數試算「會選到幾個」,為 0 才開跑。**(本套件之選池謂詞 `inRelatePool`、`needsEdgeReview` 在 `src/stores/relatedNotes.mjs`,皆純函數可唯讀試算。)
- **提示詞範例會被照抄**:範例 `"kinds":[null,"rule"]` 只是示意某方不另立主張,模型卻在兩方皆須轉主張時照填 null。範例要對應最常見之真實形狀,特殊值(null、空陣列)用文字規則說明而不放進範例;程式端對照抄之值要明文擋下,不靠後備值。
- **判準文字自相矛盾時,模型會在兩邊之間擺盪**:下游一支核對提示詞曾同時有「在各自條件下可同時成立」與「條件不同而就同一問題相反者仍是爭議」兩句,不同條件下之相反結論兩句都套得上,同一案時判對時判錯。擺盪(兩次不一致)時先找提示詞內互相衝突之句子,而不是加更多例子。本套件把「衝突」之定義收成單一常數 `CONFLICT_DEFINITION`,四支提示詞同讀(REL-14)。
- **新欄位別掛在會被整筆重寫之紀錄上**:細目原把「經哪條邊入批」記為某紀錄之子欄,實作前 grep 發現該紀錄在維護首見、換版、重設基準、pass 落帳 4 處整筆重寫——掛上去即被沖掉,要守住得 4 處各補一行(同一規則手寫 4 處＝補丁)。改為獨立欄位,不變式另列。**加欄位前先 grep 該紀錄所有寫入點。**(本套件對應:邊記錄之 `reasonCut`——鍵一旦存在即保留,守住「頂層不刪鍵」之 patch 前提〔`src/stores/edgeStore.mjs` 檔頭〕;重評進度 `edgesReviewed`／`relatedPicks` 以字串整值覆寫〔`packIds`〕。)
- **「只補空位」等於對閒置者永不生效**:夥伴筆記原設計「次標籤之後補位」,但無新主標籤之核心不會被選題選中,其新關聯永遠沒人處理——對最穩定的核心反而失效;改走重審管道。任何「順便處理」之設計,先問「沒有順便的機會時誰處理」。(本套件的候選輪巡 RS10 即為此類缺口而設:兩篇皆舊而彼此皆在前 K 名之外者從未比對,`src/core/relateSettings.mjs` 註解。)
- **用掛鉤隔離真實驗收,比調門檻可靠**:先前以拉高選題門檻隔離,漏了「待處理 ≥ 每批即入選」而失效;改以動作鏈掛鉤(選池錨點 before:非目標模式即中止)只放行要驗之路徑——不依賴對選題規則之完整記憶。代價:被擋之一般批計入「失敗」,判讀時扣除。(本套件之掛鉤:`cfg.stageOpts.<relate|project|relationIndex>.tap`、重評鏈 `cfg.stageOpts.reeval.tap`,README §10。)
- **量進料再談開不開**:開啟某條管道前先唯讀量進料(每日新增量、觸及目標之比例、全庫消化後之穩態進料),遠大於預設容量者不要擅自開;開關預設停用,容量配置交使用者——**不以截斷或過期丟棄(靜默縮減)**。(本套件:容量自洽檢核 `relateWarningsOf` 只警告「進料 > 容量」、不警告閒置;`relate.reverse.perRun`、`relate.rotation.perRun`、`relate.reeval.perRun` 預設 0。)
- **題組要用安裝方之詞彙,不是套件預設**:題組三案之現行型別寫成套件預設之「同類方法」,安裝方詞彙表是「同族關係」——模型正確指出「不在型別清單內」而判改型,我卻當成模型錯。題組執行器在呼叫 AI 前先驗每案之型別在詞彙表(`planRelateBench`／`runRelateBench` 組提示詞時驗,`--cases` 自帶題組同;`unit-relate-bench`「題組與詞彙不合 → 任何呼叫之前拋錯」案釘住),免得出題錯也燒額度。
- **判準本身含糊時,調措辭不會收斂**:「型別是否正確」在型別無定義、一對筆記常可用多種型別描述時,三輪措辭(18/20 → 21/23 → 20/26)此消彼長。換路:①把可判定之部分收斂成封閉清單(只有現行為「同類／互補」而改為「實作／延伸」算型別錯:`retypeAllowed`,依詞彙表 `relationTypeRoles`;角色不全時不設限)②判斷改為步驟式 ③模型仍偶發「改寫籠統理由時順手換型」→ 程式強制(不屬清單之改型視為同型改理由,`reviewVerdictOf` 標 `normalized`;評分與正式段共用單票函數 `rs6VoteActionOf`)。**模型自由度與標準不一致時,用程式收斂,不靠再補一句提示詞。**
- **待判要有「條件成立自動結案」的出口**:待判建議使用者依建議處置(如加一筆別名);處置完成後建議所針對之問題已不存在,但待判沒人結,永掛逾期。題組全過、單元全綠都看不出,是交付前把「使用者照建議做完之後下一輪會怎樣」走一遍才發現。**凡登錄待判(owner user),要寫明哪個可觀察條件成立時由管線自己結案,並有單元案例。**(本套件之落實:過時待判每輪結案——重評之 `reevalHoldsStale`、衝突核對／既有邊覆核〔STD-27〕;存量待判「已不再違反」結案〔STD-29,抓取套件 `closeStockHold`〕。)
- **每做完一項就跑全套,不只跑該模組之測試**:曾完成一項標準後只跑該模組之測試,接著又做了兩項,直到收尾跑全套才發現前一項留下 5 個失敗(入口漏掛、三案釘住舊詞彙形狀／domain 成員清單、撤出理由清單)。全套比事後回頭判讀便宜。**每項標準落地之檢查點＝本套件全套(`npm test`)皆綠**,才往下一項。
- **全量預演本身就是測試**(存量工具):單元案例全綠,對複本全量預演(數千件)才看到「擠標籤＋計數尾碼並存」之標籤被修成亂鍵、使該篇失去原分群——共用之概念鍵正規化先判尾碼只去最後一個「(345)」、拆不開。新進同一實作,等於新進也有此洞。**改資料之工具,先對真實全量預演、看「改了什麼」之分布與異常(如分群只失不得),再談套用。**(本套件之存量處置:`planEdgeStockFix` 預演〔不寫〕→ `applyEdgeStockFix` → `verifyEdgeStockChain` → `rollbackEdgeStockFix`,README §13。)
- **修正函數要以「修完再驗一次」測,不只測輸入→輸出一對**(字形修正 `toTw`):單元案例都是「已知輸入 → 期望輸出」,全過;存量套用後重掃才見殘留「准確」——單字修正(②)改「确」造出誤用詞(③),而③已跑過。修正函數之性質測試應是「任一不合格輸入 → 修正後 `isTw` 為真」(樣本須含「②造出③」之字)。這個洞也讓新進理由含「准确」者被正規化後仍判不合格、退回重試。現行 `toTw` 已迭代至不動點(至多 3 趟,`textForms.mjs`);本套件納入閘亦是「正規化 → `checkEdge`」(修完再驗,`src/standards/edgeGate.mjs`)。
- **修正要對準標準之「對象」**:同一內容只入庫一次之對象是文件,只刪重複之筆記而文件仍在,掃描照樣不合格——單元測試之「重跑預演為 0」才抓到。設計修法前先確認該標準檢的是哪個集合、哪個欄位。(本套件 RS3 檢「理由與沿革理由」,確定性修正亦須同時改兩處〔`scriptFixHistory`〕。)
- **題組全過不等於端對端對**:某題組 9 案兩次全過,但真實 AI 端對端第一批 20 篇就見 2 篇「非落點筆記在兩個既有類別間被平移」——題組從沒出過「非落點、含關鍵詞、可平移」這種形狀。題組只驗出過題的形狀;**新標準上線前必以真實資料在複本跑一批端對端,逐筆看去向**,看到新形狀再回補題組(一般案＋未見過之保留題)。本套件題組為合成材料(README §14),分數不代表你的庫之表現。
- **一次送審之量要有上限**:某專步原把本輪全部候選一次送審,配額設大就成單一超長提示詞(超過席位上限即整輪失敗)。比照本套件的分頁(重評、衝突核對、既有邊覆核 `pageSize` 皆預設 10 條)——中止時已判之頁照樣處置,即「逐批即存」同一原則。
- **保留題失敗先複核出題,不是改提示詞**:兩篇對同一指標之結果方向相反、條件不同——是否衝突本可爭議,不屬「判得清楚之案」→ 移出題組並附理由、以同形狀而無爭議之新題取代;提示詞不動。被用來判斷調整方向之保留題一律轉為一般案,另補未見過之保留題。
- **程式消費 AI 欄位前,先確認提示詞定義了它的語意**:衝突核對／既有邊覆核之「keep 而現行理由不合格 → 以 keep 票之理由改寫」直接拿 keep 票之 reason 當新邊理由,但兩支提示詞只對 change 定義 reason(「一句話寫出具體關聯」),keep 之 reason 只要求 ≥10 字——模型常寫「現行理由已點出…型別正確」這類評語,過得了形式閘卻不是理由。子代理之單元測試用替身寫好的理由,看不出來。**凡程式把 AI 某欄位「用作另一種東西」,先讀提示詞找該欄位對該裁決之定義。**
- **補定義也會改變裁決邊界——改提示詞後必以題組重跑**:第一版補法是「keep 之 reason 亦須寫『甲說…；乙說…』」,單元全綠;題組正式重跑衝突核對之保留題兩案(現行理由未陳述雙方 → 應 change)第一次即判 keep——模型把改寫好之理由放在 keep 下,keep 與 change 之分界被這句話抹平。撤回,改為**只在需要改寫之項附逐項指示**(「現行理由未達標準…須以 change 改寫、不可 keep」;其餘項與題組逐字不變)、程式不再取 keep 票之理由。**要模型做不同之事時,改指示之對象(那一項),不改全體共用之定義**。
- **品質測試要走生產之分批,不只用同一個提示詞函數**:曾有某品質測試沿用評比題目(一次 3 篇、每篇截 6,000 字),生產則依字數打包(長文獨佔一批、18,000 字內全文進 AI)——20,000 字之樣本生產讀到 18,000 字、測試只讀 6,000 字,測的不是正式路徑。把打包抽成純函數,生產與測試共用。**「正式提示詞」包含組裝它的所有參數(預算、分批、材料截斷),不只模板**;評比工具可刻意凍結(題目指紋),驗收測試不行。(本套件評分之一頁案數＝`relate.notesPerCall`／`pageSize`,與正式段同一設定,README §14。)
- **審查子代理之報告,逐項回到改動處讀碼再接受**:報告寫得完整、測試全綠,但只有讀到 `edgeReviewSegment` keep 分支與提示詞對照,才看出 keep 理由之契約缺口;另確認了 restore 之檢核雜湊與關聯段同一 `relationTypesVersionOf(domain)`(`src/ops/noteOps.mjs`)——若不同,使用者裁示之 PASS 紀錄會被當過時而重核、再隔離成迴圈。**接受前至少核:①刪除／撤出類之新行為②跨入口共用之雜湊或鍵③提示詞與程式對欄位之約定**。
- **`toTw` 處理含違規之片段時,會連帶把「台」轉成「臺」**:先折回簡體再轉之片語上下文會把緊鄰違規字之「台」一併正規化(實測「平台数据」→「平臺數據」、「台湾」→「臺灣」,而「台」不緊鄰違規字時不動:「台下的数据」→「台下的數據」);合法而非必要之改字。不改共用件(影響判定),記錄供判讀 RS3 存量修正之 diff 時參考。
- **題組同一案兩次各判一邊＝案本身判不清,不是調提示詞之訊號**:某案(以類別泛稱推廣、出處只比最低與最高兩組)兩次分判 supported／overclaim,兩邊理由皆說得通——依「只收判得清楚之案」改列排除附理由、以同形狀而無推廣之新案取代;另一案則是同一提示詞前次全過、本次一次 unsure,重跑即過——偶發不穩,如實記錄重跑次數。**區分:兩邊理由都成立 → 案之問題;一邊明顯錯 → 提示詞或模型之問題。**
- **符合度掃描每輪跑之成本**:全量掃描逐邊讀兩端筆記(含原文材料),大庫耗時;`material` 開關幾乎不影響耗時(主耗時在讀全庫)。每輪多一次全量換「違反數每輪可見、增加即報」;`relate.standards.scanEachRun` 預設關閉,由使用端依庫規模開啟(README §13)。
  - **複量**:庫未倍增而耗時曾達 3.5～4.4 倍。教訓:**「庫再大一倍時重量」之觸發條件只看資料量,漏了「掃描之實作／範圍改變」**——抓取、摘要、關聯三次抽套件與新標準(掃全部線索、讀材料)各自加成本,沒有人回頭量。CPU 剖析找到三處實作效率(slug 正則近平方、逐碼位配置字串、逐筆走寫入路徑),等價改寫後耗時降至約三分之一、各項標準結果逐字相同。**往後新增或改寫掃描之標準時,改後即量一次全量**(以 `auditRelateStandards({ stores, domain, locale }, { material: true })` 對庫複本計時;唯讀)。
- **收尾時以項目編號機械比對「待辦表 × 進度表」**:有一項標「採」卻從未實作,進度表只寫「某批收回」——據進度表寫「已全部完成」,直到最後盤點逐一 grep 各項編號才發現。**宣稱一批做完前,對待辦表每個編號在進度與程式中各找一個落點(grep 編號＋關鍵行為),找不到即未做**;不以「批收回」代替逐項。
- **逐項指示對真實模型有效,閘仍必要**:存量 RS2／RS8 而理由不合格之 10 條,兩席 20 票全數依「現行理由未達標準須 change」改寫;但一票把原理由之「4447 個變數」寫成「447 個」——自生無據數字,被納入閘(RS8)擋下、改採另一席之理由。**席位聽話不代表輸出合格,改寫理由一律再過閘**。
- **無聲截斷看「上限處的突起」找得到**:某欄位 60 字上限——庫中恰 60 字者數十篇、59 字者個位數(自然分布不會在上限處突起),抽 8 篇有 7 篇斷在數字中(「…2026-08-」)。**任何 `slice(0, N)` 之欄位,先數「恰等於 N」與「N−1」之篇數**;突起即被截。修法比照關聯理由:於上限內最後句讀處截並記錄,無句讀則全文保留(`cutAtBoundary`,兩處同一實作;本套件理由逾 `REASON_MAX_CHARS`〔200〕即如此,並記 `reasonCut`)。
- **測試注入之日誌字樣須與程式現行輸出逐字相同**:曾有重評逾次之 WARN 改為「已登錄待判（RS5）」後,使用端巡檢白名單與其測試注入字樣仍是舊的「以保留結案」——測試綠(它驗的是舊字樣不被報)、實際 WARN 卻會被報為未知警告。改 WARN 字樣時 grep 舊字樣於 src／test 全範圍,白名單與測試一併改;測試字樣最好與產生端之單元測試斷言同一字串。本套件以 `src/logContract.mjs`(`RELATE_LOG_KNOWN`／`RELATE_LOG_MUST_SEE`／`RELATE_LOG_PARSE`)為字樣單一來源,`unit-relate-log-contract` 對實際產出驗。
- **「標準已建」不等於「只告警／計數」清單那一格已處置——逐項回到程式核實**:各模組之「只告警／計數」清單交數個子代理唯讀歸類(每格 file:line),再由主代理逐項核對:找出 3 個缺口(1 個已觀察)、1 個巡檢誤報、1 個共用函數之擴充區字缺陷、4 處文件與程式不符——全是先前「盤查全部 ✅」時沒看到的。**收尾盤查之「完成」須以逐格核實之表為據**,不以帳本條目存在推定。
